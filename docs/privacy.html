Local is a place.
Privacy is a practice.

Speech recognition runs on your device. Where text goes next—and what you choose to keep—still matters.

This describes the current local development architecture, not the older v0.2.0 APK. It is not a qualified release or a guarantee about every receiving app. Physical-device and editor checks remain open.

Speech and model downloads

Lip's active development controllers do not offer OpenAI login or cloud speech processing. Clean and Pro recognize English locally. There is no second cloud cleanup model. A model download contacts its download host; the host receives normal network metadata such as your IP address. Downloading a model is not uploading your recordings.

Recordings are processed on the device. Local processing does not mean temporary audio files, memory or operating-system diagnostics can be promised securely erased under every interruption. Do not treat a development build as a certified confidential-data system.

Direct insertion and permissions

On macOS, Microphone access enables recording, Input Monitoring supports the Fn gesture, and Accessibility supports focused-field and caret checks for insertion. Lip checks the destination and retains text in Review when it cannot verify safe insertion. It does not press Send or Enter to submit your transcript. Some real-editor integrations are still unconfirmed.

The direct-insertion path does not replace the clipboard. Explicit Copy actions do. Once text is inserted or copied into another app, that app's storage, syncing and privacy behavior apply; Lip cannot retract those copies.

Transcript history is not a typing archive

Android's existing encrypted transcript history is on by default. It can retain original and processed dictation on that device. “Keep encrypted transcript history” in Settings stops new saves when switched off; it does not erase prior entries. Existing transcripts and migration data are preserved rather than silently deleted.

The Mac app keeps its current transcript in memory for Review; it does not currently provide the matching persistent Android transcript archive. Restarting can lose that in-memory result. Cross-platform history parity remains unfinished.

There is no enabled archive of all typed or swiped text, no cloud history sync and no automatic import of Gmail, Outlook or WhatsApp history. Those are separate future features. Dictionary learning and any future journal must not be treated as the same consent.

Keyboard context and reactions

The Android keyboard uses limited editor context in memory for predictions and guarded editing. It does not need to upload that context for these features. Protected-field behavior relies on editor flags; ordinary text fields can still contain secrets, and Lip cannot promise to detect them all.

Emoji and local GIF searches stay inside the keyboard. Emoji recents are off by default; opting in remembers picks in memory only for the current field, not a permanent emoji history. Unicode artwork is rendered by Android's font.

The optional encrypted clipboard archive is off by default. Its current bounded implementation is separate from transcript history and future typing history; it is not the proposed 100 MB archive. Explicit clipboard actions can move content outside Lip. Clipboard consent does not enable a typing journal.

Sending a GIF uses a supported editor's content-insertion route. The destination can retain it. A dispatch result alone does not prove the receiving app displayed the image; unsupported hosts must not be described as supported.

Old credentials and future cloud features

The local takeover removed active cloud-login and cleanup entry points. That does not mean old encrypted credentials or provider authorizations were erased or remotely revoked. Existing data was preserved. Revoking an old authorization is a separate account action.

Translation—including an optional ChatGPT backend—sticker-pack import, WeChat-specific assets, and encrypted history sync are future work, not active services. Any future cloud provider, account flow or text upload requires its own explicit disclosure and consent.

macOS recovery audio (development source)

In the forthcoming macOS build, a failed transcription or a recording with an unprocessed overrun can leave the original audio in a private local recovery folder. These files are unencrypted by Lip, even when transcript history is off, and remain until you remove them manually. Lip restricts folder/file access and marks recovery storage as excluded from system backup, but that is not a guarantee about third-party backup tools. Cancel deletes the current recording, not older recovery files. Lip does not upload recovery audio. This describes development source, not a new published Mac installer.

This preview website

This GitHub Pages website uses local images, styles, scripts and system fonts. It has no analytics, advertising, account form or live transcription demo. It does not request microphone or clipboard access, save your gallery choices, or contact third-party asset services. Source-code links open external sites only when you follow them.

Full screenshots are available alongside the keyboard-detail crops. They show synthetic editors in an Android emulator, not Jared's messages, a physical phone or a fabricated product mockup. GitHub hosts this site and the release downloads and may process request metadata under its own privacy policy. Downloading the APK does not grant this website microphone or clipboard access.
